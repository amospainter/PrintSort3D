# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**PrintSort3D** — a local web app for cataloging STL/3MF/OBJ 3D print files: scans configured folders, generates a thumbnail per file (extracted directly from Bambu Lab `.3mf` files, or rendered in-browser otherwise), and lets the user tag/annotate each file. Two packages: `server/` (Express + TypeScript API, SQLite) and `client/` (React + TypeScript, Vite, three.js).

Full details: [README.md](README.md), [docs/architecture.md](docs/architecture.md), [docs/api.md](docs/api.md), [docs/testing.md](docs/testing.md).

## Commands

```sh
npm run install:all          # install root + server + client deps
npm run dev                  # run server (:3001) and client (:5173) together
npm test                     # run server tests then client tests
npm test --prefix server     # server tests only
npm test --prefix client     # client tests only
npx vitest run <file>        # single test file (run from server/ or client/)
npx tsc -p tsconfig.json --noEmit   # server typecheck (from server/)
npx tsc -b --noEmit                 # client typecheck (from client/)
npm run build --prefix server       # compile server to server/dist
npm run build --prefix client       # build client to client/dist
```

There is no separate lint command wired up at the root; `client/package.json` has `npm run lint --prefix client` (oxlint).

## Architecture — the parts that aren't obvious from file names alone

Read [docs/architecture.md](docs/architecture.md) first; the essentials:

- **`node:sqlite`, not `better-sqlite3`.** The server uses Node 22.5+'s built-in `node:sqlite` (`server/src/db.ts`) specifically to avoid a native-addon build step. Its API (`db.prepare(sql).get/all/run(...)`) is close enough to `better-sqlite3` to read the same way, but don't add `better-sqlite3` back without a strong reason — that was a deliberate Windows-compatibility fix.
- **`sharp` is a deliberate exception to the no-native-addons rule.** It's used for PNG→WebP conversion of embedded 3MF images (`server/src/assets.ts`). Unlike `better-sqlite3`, `sharp` ships prebuilt platform binaries that `npm install` fetches directly — no local compilation. If you're tempted to avoid a dependency for "native addon" reasons, check whether it ships prebuilt binaries first; that's the actual criterion, not "native vs. pure JS".
- **Thumbnails come from two different pipelines, not one.** For Bambu Lab `.3mf` files, `server/src/threeMf.ts` unzips the file and pulls out an embedded plate PNG + `project_settings.config` directly — no rendering. Everything else (`.stl`, `.obj`, non-Bambu `.3mf`) has no embedded thumbnail, so `client/src/ThumbnailGenerator.tsx` renders one in the browser (imperative three.js, not `@react-three/fiber`) and POSTs the PNG back to `/api/files/:id/thumbnail` to cache server-side. When touching thumbnail logic, check which pipeline actually applies to the file type you're changing.
- **`ThumbnailGenerator.tsx` is deliberately imperative, not declarative R3F.** It was originally built on `@react-three/fiber`'s `<Canvas>`, but React 18 StrictMode's dev-mode double-invoke of effects combined with a naive "only run once" ref guard caused the real (surviving) mount to never fire — the guard's `true` value survived the StrictMode remount and blocked it. It was rewritten as a single `useEffect` with a plain `THREE.WebGLRenderer` on a detached canvas, guarded only by a per-effect `cancelled` closure flag (not a ref that persists across remounts). If you touch this file, keep that guard pattern — a `useRef` "already started" flag is exactly the failure mode to avoid here.
- **`missing` files are flagged, not deleted.** `server/src/scanner.ts`'s `runScan()` never deletes a `files` row for a file it can't find; it sets `missing = 1` so tags/notes/thumbnails survive a temporarily-unplugged drive, and un-flags automatically if the file reappears.
- **Env-var path overrides exist for testability, not runtime configuration.** `db.ts`, `config.ts`, and `paths.ts` read `DB_PATH` / `CONFIG_PATH` / `THUMBNAILS_DIR` / `ASSETS_DIR` env vars with on-disk defaults, purely so test files can point each isolated test run at its own temp directory. See [docs/testing.md](docs/testing.md) for the dynamic-`import()` pattern this requires (static imports are hoisted above where a test sets these env vars, so tests must `await import(...)` after setting them). This also means it's never safe to verify server behavior against the real running dev server's `config.json`/`catalog.db` — use the same temp-dir-and-scratch-port pattern the tests use if you need to check something live.
- **`runScan()` is async.** It awaits WebP conversion for every new/changed 3MF file's embedded images. Every call site (including in tests) must `await` it — a stray non-awaited call will race the response/assertions against a scan that's still writing to the DB.
- **The `files` table has grown by migration, not just `CREATE TABLE`.** `embedded_images_json`, `dimension_x/y/z`, and `scanner_version` were each added after the table already existed in the wild, via `ALTER TABLE ... ADD COLUMN` guarded by a `pragma_table_info` check in `db.ts` (run on every startup, no-ops if the column's already there). If you add another column to an existing table, follow that pattern — `CREATE TABLE IF NOT EXISTS` alone does nothing for databases that already exist.
- **Model dimensions are computed server-side at scan time, not client-side per view.** `server/src/dimensions.ts` parses STL/OBJ bytes and 3MF zipped XML directly — no three.js, no rendering, since a bounding box is pure math. The client just reads `file.dimensions` from the API; it doesn't reparse the model. When touching this, remember real Bambu/OrcaSlicer 3MF exports split geometry across multiple `3D/Objects/object_N.model` part files (the root `3D/3dmodel.model` is often just a manifest) — `computeDimensions` unions vertices across every `.model` entry in the zip, not just the first one found. An earlier version that stopped at the first entry silently returned `null` dimensions for every real Bambu file; `dimensions.test.ts` has a regression test for exactly this.
- **`scanner_version`, not "is the column still NULL", drives backfill on rescan.** `runScan()` only reprocesses a row when its `mtime` changed *or* its `scanner_version` (in `scanner.ts`, `CURRENT_SCANNER_VERSION`) is behind — bump that constant whenever new scan-time processing is added so existing rows pick it up on their next rescan. This exists because the first version of this backfill logic checked `dimension_x IS NULL` instead, which broke two ways at once: files whose `mtime` never changes (the common case — nothing on disk actually changed) never got the new columns computed no matter how many times you rescanned, *and*, after fixing that, a file with no parseable geometry (where `NULL` is the legitimately correct and permanent result) got needlessly reprocessed on literally every scan forever. `scanner.test.ts` has regression tests for both failure modes — don't reintroduce either by going back to inferring "needs processing" from a nullable data column.
- **`server/src/app.ts` vs `server/src/index.ts`.** `createApp()` in `app.ts` builds the Express app without binding a port, specifically so `routes.test.ts` can drive it directly with Supertest. `index.ts` is the actual entry point (imports `db`/`paths` for their side effects, then calls `createApp().listen(...)`).
- **A single corrupt file must not abort `runScan()` for every other file.** `adm-zip`'s `entry.getData()` throws on a malformed zip entry (`ADM-ZIP: Descriptor data is malformed` — hit for real against a real Bambu 3MF export), so `listThreeMfImages()`/`extractThreeMfData()`/`parseThreeMfDimensions()` each wrap their per-entry `getData()` calls individually and skip the bad entry rather than let it propagate. `runScan()`'s per-file loop body is also wrapped in `try/catch` as a second layer, and `POST /api/scan`'s handler has its own `try/catch` as a last resort (Express 4 doesn't auto-catch rejections from async route handlers — an uncaught one can take down the whole process, not just fail the one request). If you add new per-file processing to the scanner, keep it inside that per-file `try/catch`, and if it reads zip entries, wrap each `getData()` call individually rather than trusting the archive is well-formed just because `new AdmZip()` succeeded.
- **Geometry-hash duplicate detection tolerates vertex order/rounding, not rotation or scale.** `server/src/fingerprint.ts`'s `computeGeometryHash` (fed vertices from the shared `forEachVertex` walker in `server/src/geometryParse.ts`, which `dimensions.ts` also uses for bounding boxes) normalizes to the bounding box's min corner, rounds to 0.01mm, and sorts before hashing — so the same model re-exported to a different format hashes identically even though triangle order differs between exporters. It does *not* detect the same model rotated or scaled, since that's a materially harder problem (mesh alignment) than this v1 scope covers. `content_hash` (raw SHA-256 of file bytes) is the separate, exact-byte-match signal — use whichever `matchType` the UI needs to distinguish.
- **Archive (`.zip`) entries are read live, not cached or indexed.** `server/src/archive.ts` lists/reads model files inside a `.zip` on every request via `adm-zip`, unlike 3MF's embedded images which get cached as WebP under `ASSETS_DIR` at scan time. This was a deliberate scope cut — archive contents have no `files` rows of their own (no tags/notes/duplicate-hashing apply to them), so there's nothing to cache against. If that changes, look at how `assets.ts`/`cacheThreeMfImages` cache keys off `fileId` for the pattern to follow.
- **`CURRENT_SCANNER_VERSION` is at 8** as of the server-baked render mesh (see the baked-mesh bullet below). v6 was multi-color filament extraction (`parseFilaments` in `threeMf.ts` — the full `filament_colour`/`filament_type` arrays, not just the first slot that `filamentColor`/`filamentType` still expose — stored as `files.filaments_json` and surfaced as `file.filaments`, rendered as swatches on the Detail page's "Slicer metadata"). v5 was plate-name extraction (`computePlateNames`, folded into each `PlateInfo.name` in `files.plates_json`). Bump it again for the next new scan-time computation, per the `scanner_version` backfill mechanism described above. Forgetting this bump is exactly what happened at v3: `computePlateBuildIndices` was added without bumping the version, so already-scanned rows silently never got `buildItemIndices` computed until the next bump forced a reprocess.
- **The viewer loads a server-baked binary mesh, not the source file.** Parsing a big model in the browser (a 9 MB 3MF unzips to ~47 MB of XML → multi-second `DOMParser` + `querySelectorAll` jank) is the bottleneck. `server/src/meshBake.ts` `bakeModel` parses STL/OBJ/3MF once at scan time into `{ positions: Float32Array, indices: Uint32Array, paint: Uint8Array | null }[]` — one part per 3MF `<build><item>` (STL/OBJ = one non-indexed part). For 3MF it resolves the `<build>` → `<object>` → `<component p:path>` graph itself and **bakes each item's accumulated affine transform into the vertices** (so a negative-determinant transform flips winding); no three.js on the server. `server/src/assets.ts` `cacheBakedMesh` serializes to the `"PSM1"` blob (`partCount`, then per part `floatCount, indexCount, flags, Float32 positions, Uint32 indices, Uint8 paint`), `gzipSync`es it, and writes `ASSETS_DIR/<fileId>/mesh.bin.gz`. `GET /api/files/:id/mesh` serves it with `Content-Encoding: gzip`; `file.meshUrl` is that URL or null. Client: `loadModel.ts` `loadBakedMesh` turns the blob into a `THREE.Group` (one `Mesh` per part, in part order — so `visibleChildIndices` plate toggling and `frameObject` still work) in ~10 ms, bypassing `STLLoader`/`OBJLoader`/`ThreeMFLoader` entirely (those stay only for `.zip` archive entries and files with no baked mesh yet). Each part's per-triangle filament slots ride on `mesh.userData.paint`.
  - **Per-triangle paint** (multi-material / AMS 3MFs) is folded into the bake. `server/src/paintColor.ts` `decodePaintColor` is a **clean-room** bit-reader for the `paint_color="1C"`-style `<triangle>` attribute (Bambu/Orca/PrusaSlicer `TriangleSelector` serialization), written from the wire format — read the string right-to-left, hex digits are 4 bits LSB-first; `splitSides = code & 0b11`; leaf state is `code >> 2`, or `nextNibble() + 3` when the low nibble is `0b1100` — *not* copied from the AGPL reference. `state` is the 1-based extruder → filament slot `state - 1`; unpainted triangle → slot 0; a **split** triangle is approximated by its dominant (most-frequent) leaf state (full midpoint subdivision is a later follow-up). Client `applyPaintColors(object, filamentColors)` reads `mesh.userData.paint`, converts to non-indexed geometry and sets a normalized `color` attribute + `vertexColors` material; `removePaintColors` restores. The Detail page's "Show painted colors" checkbox toggles it (default off; shown when `file.meshUrl && file.filaments.length > 1`).
- **Build-plate size: parsed per-file for Bambu/Orca 3MFs, configured default for everything else.** `parsePlateSize` reads `printable_area` (or legacy `bed_shape`) from `project_settings.config` and takes its bounding box. The API's `file.bedSize` is always populated — the parsed size when known, else `config.json`'s `defaultPlateSize` (user-editable via `GET`/`PUT /api/settings`, defaults to 256×256mm) — with `file.plateSizeSource` saying which. The client viewer (`ModelViewer.tsx` / `loadModel.ts`) draws the grid at those exact dimensions and frames the camera to fit the larger of model-or-bed; with no `bedSize` at all (archive entries) it falls back to the old footprint-plus-padding grid.
- **`/api/raw/:id` has a path-traversal guard.** It resolves `root.path + relativePath` and rejects (400) if the result would land outside the root. `relative_path` is normally scanner-controlled and safe, but the guard exists because that value is trusted DB data, not re-validated per request — if you add new ways to write `relative_path`, make sure this guard still holds.
