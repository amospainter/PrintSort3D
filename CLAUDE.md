# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

**PrintSort3D** — a local web app for cataloging STL/3MF/OBJ 3D print files: scans configured folders, generates a thumbnail per file (extracted directly from Bambu Lab `.3mf` files, or rendered in-browser otherwise), and lets the user tag/annotate each file. Two packages: `server/` (Express + TypeScript API, SQLite) and `client/` (React + TypeScript, Vite, three.js).

Full details: [README.md](README.md), [docs/architecture.md](docs/architecture.md), [docs/api.md](docs/api.md), [docs/testing.md](docs/testing.md).

## Commands

```sh
npm run install:all          # install root + server + client deps
npm run dev                  # run server (:3001) and client (:5173) together
npm test                     # run server tests then client tests
npm test --prefix server     # server tests only
npm test --prefix client     # client tests only
npx vitest run <file>        # single test file (run from server/ or client/)
npx tsc -p tsconfig.json --noEmit   # server typecheck (from server/)
npx tsc -b --noEmit                 # client typecheck (from client/)
npm run build --prefix server       # compile server to server/dist
npm run build --prefix client       # build client to client/dist
```

There is no separate lint command wired up at the root; `client/package.json` has `npm run lint --prefix client` (oxlint).

## Architecture — the parts that aren't obvious from file names alone

Read [docs/architecture.md](docs/architecture.md) first; the essentials:

- **`node:sqlite`, not `better-sqlite3`.** The server uses Node 22.5+'s built-in `node:sqlite` (`server/src/db.ts`) specifically to avoid a native-addon build step. Its API (`db.prepare(sql).get/all/run(...)`) is close enough to `better-sqlite3` to read the same way, but don't add `better-sqlite3` back without a strong reason — that was a deliberate Windows-compatibility fix. `db.ts` sets `journal_mode=WAL`, `synchronous=NORMAL` (safe under WAL, drops an fsync per commit — a real scan-throughput win), `foreign_keys=ON` (the `file_tags` cascade is otherwise a silent dependency on node:sqlite's default), and `busy_timeout=5000`. Indexes: the two hash columns plus `added_at`/`mtime`/`size_bytes`/`filename`/`root_id`/`ext` (every `GET /api/files` orders by one of the first four and often filters `ext`/`root_id`).
- **`sharp` is a deliberate exception to the no-native-addons rule.** It's used for PNG→WebP conversion of embedded 3MF images (`server/src/assets.ts`). Unlike `better-sqlite3`, `sharp` ships prebuilt platform binaries that `npm install` fetches directly — no local compilation. If you're tempted to avoid a dependency for "native addon" reasons, check whether it ships prebuilt binaries first; that's the actual criterion, not "native vs. pure JS".
- **Thumbnails are rendered entirely server-side at scan time — there is no client thumbnail generation.** Two sources: (1) Bambu Lab `.3mf` files carry an embedded plate PNG, pulled out by `server/src/threeMf.ts` (no rendering). (2) Everything else (`.stl`, `.obj`, non-Bambu `.3mf`) is drawn by `server/src/thumbnail.ts` `renderBakedThumbnail` — a **CPU-only software rasterizer** (z-buffer, flat two-sided Lambert shading, 2× supersample → `sharp` PNG encode) fed the already-baked `BakedPart[]` from `meshBake.ts`. **No WebGL / three.js / GPU on the server** — it must run headless in a minimal Docker container. `scanner.ts` `processFile` bakes once, caches the mesh, and (unless the file supplied its own embedded thumbnail) renders from those same parts; `applyRenderedThumbnail` overwrites, so a rescan replaces a stale/old thumbnail. Camera framing + lights mirror the in-browser viewer so a thumbnail matches opening the file (tighter zoom — 1.32× vs the viewer's 1.6× — since there's no bed to keep in frame). All thumbnails write through `saveThumbnail()` to `ASSETS_DIR/<fileId>/thumbnail.png` alongside every other per-file artifact (embedded-image WebPs, baked `mesh.bin.gz`), so `deleteCachedImages(fileId)` is the single teardown path. `db.ts` has a one-time startup migration that relocates PNGs from the old standalone `thumbnails/` layout (legacy `THUMBNAILS_DIR` env var, or `server/thumbnails/`). `GET /api/files/:id/thumbnail` only *serves* the cached PNG; there is no upload endpoint (removed with the client generator).
- **Theme is CSS-token-only; the key color is `--accent`.** `client/src/index.css` defines the full palette as CSS custom properties on `:root` (light) with a dark override. Theme resolution has three states: no `[data-theme]` attr = follow the OS (`@media (prefers-color-scheme: dark)`, guarded `:root:not([data-theme='light'])`), `[data-theme='dark']` / `[data-theme='light']` = explicit override that beats the OS. The dark token block is **deliberately duplicated** — once inside the media query, once in `:root[data-theme='dark']` — keep the two copies in sync. `client/src/theme.ts` owns the `printsort3d-theme` localStorage key (per-browser, not server config); `ThemeToggle.tsx` (sidebar footer) is the System/Light/Dark control; an inline script in `client/index.html` applies the stored value before first paint to avoid a flash. Nothing hard-codes a color — every accent surface reads `var(--accent*)`. Filament swatches and `--warn`/`--danger` are semantic, not the accent.
- **`missing` files are flagged, not deleted — but can be purged on request.** `runScan()` never deletes a `files` row for a file it can't find; it sets `missing = 1` so tags/notes/thumbnails survive a temporarily-unplugged drive, and un-flags automatically if the file reappears. **A whole root that's unreachable is exempt** — if `root.path` doesn't exist, or it walked to zero files but has catalogued rows (an unmounted share), every row under it is left untouched rather than flagged missing then un-flagged on the next scan (`unavailableRootIds` in `runScan`). Removing them from the catalogue is explicit: `DELETE /api/files/:id` (409 unless `missing = 1`) or `POST /api/files/purge-missing` (`?root=` scopes it) — both drop the row, its tags, and its `ASSETS_DIR/<id>/` tree. `GET /api/files?missingOnly=1` lists them (Library `/?missing=1` view, sidebar "Missing" link, Settings "Missing files" section). `index.ts` also runs `pruneOrphanAssets()` on every startup — deletes any `ASSETS_DIR/<n>/` whose `<n>` isn't a live `files.id` (leftovers from a purge or a crash mid-teardown).
- **The scan pipeline is split into extract (pure) and write (DB).** `server/src/scanArtifacts.ts` `extractArtifacts(fileId, fullPath, ext)` does *all* the per-file work that touches only the filesystem — bake, dimensions, hashes, thumbnail render, WebP conversion, 3MF/archive metadata — and writes the derived files under `ASSETS_DIR`, returning a plain `FileArtifacts` struct with **no DB access**. `scanner.ts` `writeArtifacts(fileId, artifacts)` does the DB updates (at most two `UPDATE`s per file, down from six). This split is what lets the extract half run in a worker (`scanWorker.ts` / `scanPool.ts`): set `SCAN_WORKERS=<n>` to parallelise a big scan across cores; the DB stays single-writer on the main thread. Off by default → everything runs inline (`extractArtifactsPooled` falls back to `extractArtifacts`), which is the only path tests exercise. Between files the scan `await`s `setImmediate` so the API stays responsive even inline.
- **One scan at a time, with progress / cancel / reprocess.** `runScan()` is guarded by a module-level `inFlightScan` promise; a concurrent call returns the in-flight result. `getScanProgress()` exposes a live `ScanProgress` (phase, total, processed, currentFile, add/update/missing counts, timing) — `GET /api/scan/status` returns `{ scanning, progress, pendingReprocess }`. `requestScanCancel()` (`POST /api/scan/cancel`) stops the scan after the current file; a cancelled scan skips the missing-flag pass (it never finished looking) and is resumable by re-running. `runScan({ mode })`: `'scan'` (default — walk the filesystem), `'reprocess-stale'` (no walk — re-run processing on rows with `scanner_version < CURRENT`, the "resume interrupted scan" / "backfill after a version bump" case), `'reprocess-all'` (every non-missing row). `pendingReprocessCount()` drives the Settings "N files need a metadata update" prompt. `rescanFile()` (single-file) is not gated by the mutex — `PRAGMA busy_timeout` covers the contention.
- **The scanner follows directory symlinks / junctions.** `walk()` stats through symlink entries (which `Dirent.isDirectory()` reports as neither file nor dir) and recurses, with a resolved-realpath `seen` set to break symlink cycles. Common on Windows (junctioned models folder) and NAS setups.
- **Security middleware is all opt-in via env, wired in `server/src/security.ts` / `createApp()`.** Off by default so a localhost user sees no change. `PRINTSORT_PASSWORD` → HTTP Basic on every request (browser handles the prompt; no client code). `PRINTSORT_CORS_ORIGINS` (comma list) → the *only* way to get CORS headers at all (default: none — same-origin covers the Docker single-port deploy and the Vite proxy). `PRINTSORT_READONLY=1` → 403 every mutation. `PRINTSORT_ROOTS_LOCKED=1` → 403 `PUT /api/roots`. **Always on:** a CSRF guard refusing any mutating request whose `Origin` is neither same-origin nor allowlisted, and `PUT /api/roots` validates each entry (absolute path, exists as a directory unless already configured). `index.ts` binds `HOST` (default `127.0.0.1`; the Docker image sets `0.0.0.0` and `docker-compose.yml` publishes loopback-only). The Vite dev proxy rewrites `Host`+`Origin` to the target so the dev client counts as same-origin (`client/vite.config.ts`). Coverage: `security.test.ts`.
- **Env-var path overrides exist for testability, not runtime configuration.** `db.ts`, `config.ts`, and `paths.ts` read `DB_PATH` / `CONFIG_PATH` / `ASSETS_DIR` env vars with on-disk defaults, purely so test files can point each isolated test run at its own temp directory. See [docs/testing.md](docs/testing.md) for the dynamic-`import()` pattern this requires (static imports are hoisted above where a test sets these env vars, so tests must `await import(...)` after setting them). This also means it's never safe to verify server behavior against the real running dev server's `config.json`/`catalog.db` — use the same temp-dir-and-scratch-port pattern the tests use if you need to check something live.
- **Watched roots are `config.json` roots *plus* env-derived "managed" roots, unioned on every `loadConfig()`.** `PRINTSORT_MODELS_DIR=<dir>` turns every immediate subdirectory of `<dir>` into a root (label = dir name); `PRINTSORT_ROOTS` is an explicit `;`/newline list of `Label=/path` or `/path`. Both are re-read each call (a new mount appears with no restart) and tagged `managed: true`. `saveConfig()` strips managed roots before writing — they're never persisted — and `PUT /api/roots` neither removes them nor deletes their files when a payload omits them. `index.ts` fires one `runScan()` after `listen()` when `SCAN_ON_STARTUP` is truthy. The Docker image sets `PRINTSORT_MODELS_DIR=/models` + `SCAN_ON_STARTUP=true`, so a `-v host:/models/<name>:ro` mount is a self-registering, auto-scanned source. Client shows managed roots in Settings as "from environment" with no Remove button. Regression coverage: `config.test.ts`.
- **`runScan()` is async.** It awaits WebP conversion, thumbnail rendering, and a `setImmediate` yield per file. Every call site (including in tests) must `await` it — a stray non-awaited call will race the response/assertions against a scan that's still writing to the DB.
- **The `files` table has grown by migration, not just `CREATE TABLE`.** `embedded_images_json`, `dimension_x/y/z`, `scanner_version`, … `mesh_path`, `slice_info_json` were each added after the table already existed in the wild, via `ALTER TABLE ... ADD COLUMN` guarded by a `pragma_table_info` check in `db.ts` (run on every startup, no-ops if the column's already there). If you add another column to an existing table, follow that pattern — `CREATE TABLE IF NOT EXISTS` alone does nothing for databases that already exist.
- **Model dimensions are computed server-side at scan time, not client-side per view.** `server/src/dimensions.ts` parses STL/OBJ bytes and 3MF zipped XML directly — no three.js, no rendering, since a bounding box is pure math. The client just reads `file.dimensions` from the API; it doesn't reparse the model. When touching this, remember real Bambu/OrcaSlicer 3MF exports split geometry across multiple `3D/Objects/object_N.model` part files (the root `3D/3dmodel.model` is often just a manifest) — `computeDimensions` unions vertices across every `.model` entry in the zip, not just the first one found. An earlier version that stopped at the first entry silently returned `null` dimensions for every real Bambu file; `dimensions.test.ts` has a regression test for exactly this. `geometryParse.ts` only takes the ASCII-STL path when the file actually starts with `solid` (a truncated binary STL whose size arithmetic fails would otherwise get regexed as text → garbage vertices), and logs a warning instead of silently returning `null` when a file is too big for `buffer.toString()` (V8's ~512 MB string cap — real for large ASCII scans).
- **`scanner_version`, not "is the column still NULL", drives backfill on rescan.** `runScan()` only reprocesses a row when its `mtime` changed *or* its `scanner_version` (in `scanner.ts`, `CURRENT_SCANNER_VERSION`) is behind — bump that constant whenever new scan-time processing is added so existing rows pick it up on their next rescan. This exists because the first version of this backfill logic checked `dimension_x IS NULL` instead, which broke two ways at once: files whose `mtime` never changes (the common case — nothing on disk actually changed) never got the new columns computed no matter how many times you rescanned, *and*, after fixing that, a file with no parseable geometry (where `NULL` is the legitimately correct and permanent result) got needlessly reprocessed on literally every scan forever. `scanner.test.ts` has regression tests for both failure modes — don't reintroduce either by going back to inferring "needs processing" from a nullable data column.
- **`server/src/app.ts` vs `server/src/index.ts`.** `createApp()` in `app.ts` builds the Express app without binding a port, specifically so `routes.test.ts` can drive it directly with Supertest. `index.ts` is the actual entry point (imports `db`/`paths` for their side effects, then calls `createApp().listen(PORT, HOST, ...)`).
- **List responses omit the big `slicer_metadata_json` blob; only `GET /api/files/:id` carries it.** It was measured at ~96% of a list payload (and ~96% of `catalog.db`) and nothing in the Library reads it. `routes.ts` has two queries: `BASE_QUERY` (`SELECT f.*`, for detail) and `LIST_QUERY` (explicit column list, no blob). `serializeFile(row, size, { summary: true })` drops `slicerMetadata` from the output; the client type has it `slicerMetadata?:` (present only on detail). If you add a column the Library needs, add it to `LIST_QUERY` too. **`files.duplicate_count` is a materialized column**, not a subquery — it replaced a per-row correlated `COUNT(*)` over the whole `files` table that every list query ran. `recomputeDuplicateCounts()` (`RECOMPUTE_DUPLICATE_COUNTS_SQL` in `db.ts`) refreshes it at the end of every scan, on single-file rescan, and on delete/purge; it's backfilled once on the migration. `?duplicatesOnly=1` is now `f.duplicate_count > 0` (indexed).
- **Slice estimates (print time / filament / printer) come from `Metadata/slice_info.config`.** `server/src/sliceInfo.ts` `extractSliceInfo` parses the per-`<plate>` `prediction` (seconds), `weight` (grams), `<filament used_m/used_g>`, `printer_model_id`, `nozzle_diameters`, `support_used` — Bambu Studio / OrcaSlicer only (PrusaSlicer doesn't write this file; a Bambu *export* that was never sliced has the file but no `<plate>` blocks → `null`). Stored as `files.slice_info_json`, surfaced as `file.sliceInfo` (in list *and* detail — it's small). Drives the Detail "Print estimates" section, the Library card badges, and `sort=printTime` / `sort=filament` (via `json_extract` — files without it sort as NULL, last under the default DESC). `GET /api/files` also takes `dir=asc|desc` now; per-column default in `routes.ts` `sortMap` (name→ASC, rest→DESC), mirrored client-side as `effectiveDir` in `Library.tsx`.
- **A single corrupt file must not abort `runScan()` for every other file.** `adm-zip`'s `entry.getData()` throws on a malformed zip entry (`ADM-ZIP: Descriptor data is malformed` — hit for real against a real Bambu 3MF export), so `listThreeMfImages()`/`extractThreeMfData()`/`parseThreeMfDimensions()` each wrap their per-entry `getData()` calls individually and skip the bad entry rather than let it propagate. `runScan()`'s per-file loop body is also wrapped in `try/catch` as a second layer, and `POST /api/scan`'s handler has its own `try/catch` as a last resort (Express 4 doesn't auto-catch rejections from async route handlers — an uncaught one can take down the whole process, not just fail the one request). If you add new per-file processing to the scanner, keep it inside that per-file `try/catch`, and if it reads zip entries, wrap each `getData()` call individually rather than trusting the archive is well-formed just because `new AdmZip()` succeeded.
- **Geometry-hash duplicate detection tolerates vertex order/rounding, not rotation or scale.** `server/src/fingerprint.ts`'s `computeGeometryHash` (fed vertices from the shared `forEachVertex` walker in `server/src/geometryParse.ts`, which `dimensions.ts` also uses for bounding boxes) normalizes to the bounding box's min corner, rounds to 0.01mm, and sorts before hashing — so the same model re-exported to a different format hashes identically even though triangle order differs between exporters. It does *not* detect the same model rotated or scaled, since that's a materially harder problem (mesh alignment) than this v1 scope covers. `content_hash` (raw SHA-256 of file bytes) is the separate, exact-byte-match signal — use whichever `matchType` the UI needs to distinguish.
- **Archive (`.zip`) entries are read live, not cached or indexed.** `server/src/archive.ts` lists/reads model files inside a `.zip` on every request via `adm-zip`, unlike 3MF's embedded images which get cached as WebP under `ASSETS_DIR` at scan time. This was a deliberate scope cut — archive contents have no `files` rows of their own (no tags/notes/duplicate-hashing apply to them), so there's nothing to cache against. If that changes, look at how `assets.ts`/`cacheThreeMfImages` cache keys off `fileId` for the pattern to follow.
- **`CURRENT_SCANNER_VERSION` is at 12** as of the geometry re-parse dedup (v12: `scanArtifacts.ts` derives dimensions via `dimensionsFromParts` and the geometry hash via `computeGeometryHashFromParts` from the baked mesh instead of re-parsing the file — a 3MF was unzipped and walked ~4× per scan, now once. STL/OBJ hashes/dims are byte-identical; a 3MF's are now the *built* geometry with transforms applied vs. the old raw local-vertex union). v11 was `slice_info.config` extraction (`server/src/sliceInfo.ts` — print time / filament weight+length / printer model into `files.slice_info_json`). v10 was server-side thumbnail rendering (`scanner.ts` renders a CPU thumbnail from the baked mesh for STL/OBJ/non-Bambu-3MF via `server/src/thumbnail.ts`, replacing the deleted client `ThumbnailGenerator`). v9 was the sci-notation vertex-parse fix: `meshBake.ts`/`geometryParse.ts` regexes now accept negative exponents like `1.5e-05` — the old `-?[\d.eE+]+` truncated them to `NaN`, baking a stray origin vertex that rendered as a spike to the plate corner; bumped so existing baked meshes re-bake). v8 was the server-baked render mesh (see the baked-mesh bullet below). v6 was multi-color filament extraction (`parseFilaments` in `threeMf.ts` — the full `filament_colour`/`filament_type` arrays, not just the first slot that `filamentColor`/`filamentType` still expose — stored as `files.filaments_json` and surfaced as `file.filaments`, rendered as swatches on the Detail page's "Slicer metadata"). v5 was plate-name extraction (`computePlateNames`, folded into each `PlateInfo.name` in `files.plates_json`). Bump it again for the next new scan-time computation, per the `scanner_version` backfill mechanism described above. (No bump for the `computePlateInfo` merge — `threeMf.ts` now parses `model_settings.config` once and returns both the build-index and name maps; the two old `computePlate*` functions are thin wrappers over it, output unchanged.) Forgetting this bump is exactly what happened at v3: `computePlateBuildIndices` was added without bumping the version, so already-scanned rows silently never got `buildItemIndices` computed until the next bump forced a reprocess.
- **The viewer loads a server-baked binary mesh, not the source file.** Parsing a big model in the browser (a 9 MB 3MF unzips to ~47 MB of XML → multi-second `DOMParser` + `querySelectorAll` jank) is the bottleneck. `server/src/meshBake.ts` `bakeModel` parses STL/OBJ/3MF once at scan time into `{ positions: Float32Array, indices: Uint32Array, paint: Uint8Array | null }[]` — one part per 3MF `<build><item>` (STL/OBJ = one non-indexed part). For 3MF it resolves the `<build>` → `<object>` → `<component p:path>` graph itself and **bakes each item's accumulated affine transform into the vertices** (so a negative-determinant transform flips winding); no three.js on the server. `server/src/assets.ts` `cacheBakedMesh` serializes to the `"PSM1"` blob (`partCount`, then per part `floatCount, indexCount, flags, Float32 positions, Uint32 indices, Uint8 paint`), `gzipSync`es it, and writes `ASSETS_DIR/<fileId>/mesh.bin.gz`. `GET /api/files/:id/mesh` serves it with `Content-Encoding: gzip`; `file.meshUrl` is that URL or null. Client: `loadModel.ts` `loadBakedMesh` turns the blob into a `THREE.Group` (one `Mesh` per part, in part order — so `visibleChildIndices` plate toggling and `frameObject` still work) in ~10 ms, bypassing `STLLoader`/`OBJLoader`/`ThreeMFLoader` entirely (those stay only for `.zip` archive entries and files with no baked mesh yet). Each part's per-triangle filament slots ride on `mesh.userData.paint`. **`ModelViewer` disposes the previous model** (`disposeObject3D` in `loadModel.ts`, from an effect keyed on `object` identity) when it's replaced or the viewer unmounts — three.js has no finalizer, so without this every file opened leaked its vertex buffers. The shared module-level `BAKED_GRAY` material is never disposed (every baked mesh reuses it). `Detail.tsx` memoizes `filamentColors` so the paint effect doesn't re-run on every keystroke.
  - **Per-triangle paint** (multi-material / AMS 3MFs) is folded into the bake. `server/src/paintColor.ts` `decodePaintColor` is a **clean-room** bit-reader for the `paint_color="1C"`-style `<triangle>` attribute (Bambu/Orca/PrusaSlicer `TriangleSelector` serialization), written from the wire format — read the string right-to-left, hex digits are 4 bits LSB-first; `splitSides = code & 0b11`; leaf state is `code >> 2`, or `nextNibble() + 3` when the low nibble is `0b1100` — *not* copied from the AGPL reference. `state` is the 1-based extruder → filament slot `state - 1`; unpainted triangle → slot 0; a **split** triangle is approximated by its dominant (most-frequent) leaf state (full midpoint subdivision is a later follow-up). Client `applyPaintColors(object, filamentColors)` reads `mesh.userData.paint`, converts to non-indexed geometry and sets a normalized `color` attribute + `vertexColors` material; `removePaintColors` restores. The Detail page's "Show painted colors" checkbox toggles it (default off; shown when `file.meshUrl && file.filaments.length > 1`).
- **Build-plate size: parsed per-file for Bambu/Orca 3MFs, configured default for everything else.** `parsePlateSize` reads `printable_area` (or legacy `bed_shape`) from `project_settings.config` and takes its bounding box. The API's `file.bedSize` is always populated — the parsed size when known, else `config.json`'s `defaultPlateSize` (user-editable via `GET`/`PUT /api/settings`, defaults to 256×256mm) — with `file.plateSizeSource` saying which. The client viewer (`ModelViewer.tsx` / `loadModel.ts`) draws the grid at those exact dimensions and frames the camera to fit the larger of model-or-bed; with no `bedSize` at all (archive entries) it falls back to the old footprint-plus-padding grid.
- **`/api/raw/:id` has a path-traversal guard.** `resolveFilePath` resolves `root.path + relativePath` and rejects (400) unless the result *is* the root or sits under `root + path.sep` (a boundary check, not a bare `startsWith` — that would accept a sibling `<root>-backup/…`). `relative_path` is normally scanner-controlled and safe, but the guard exists because that value is trusted DB data, not re-validated per request — if you add new ways to write `relative_path`, make sure this guard still holds.
- **"Open in slicer" is a client-side download, not a server-side spawn.** An earlier version had `POST /api/files/:id/open` `spawn` Bambu Studio on the host — which only worked when the browser and server were the same machine, and never in Docker (no GUI in the container, and the file path is a container path). That route, `server/src/openInApp.ts`, and the `slicerCommand` config field are all gone. The Detail page's "Download to open" button is now just an `<a download>` pointing at `GET /api/raw/:id?download=1` (which adds `Content-Disposition: attachment`); the browser saves the model and the user's OS file association opens it in their slicer. Works identically local, LAN, and Docker.
- **The viewer auto-prefers the raw source model over the baked mesh for small files.** [Detail.tsx](client/src/pages/Detail.tsx) `FULL_MODEL_AUTO_BYTES` (5 MB): under that size, `loadFull` defaults `true` so the browser parses the actual `.stl`/`.obj`/`.3mf` (three's own loaders) instead of loading `mesh.bin.gz` — the bake is a main-thread-jank mitigation that only earns its keep on large files. The "use fast mesh" / "Load full model" toggle still flips it manually. **Painted colours only exist in the baked mesh** (`mesh.userData.paint`), so ticking "Show painted colors" forces `preferRaw` off regardless of size (`preferRaw={loadFull && !painted}`); the paint checkbox is shown whenever `file.meshUrl && file.filaments.length > 1`. Making paint render on the raw-loader model is a deferred item — see [docs/backlog.md](docs/backlog.md).
- **Deferred / intentionally-scoped-out work lives in [docs/backlog.md](docs/backlog.md).** Check there before assuming a missing capability is an oversight.
